# 应急响应流程

扫描过程中出现异常时，按顺序执行。目标只有一个：**先控制影响，再查原因，最后才考虑继续**。

## 触发条件

- 工具异常退出、超时、崩溃（panic / out of memory / fatal error）
- 目标出现业务异常迹象（5xx 增多、连接被大量重置）
- 误触范围外资产
- 客户要求立即暂停
- 执行人判断存在风险

## 五步处置

### 1. 立即停止

终止当前扫描进程和所有子进程，不再对目标发起新请求。脚本已自动完成这一步。

### 2. 保留现场

不要删除运行目录。里面应包含：

- `manifest.json`：目标、工具、完整命令、时间、授权方
- `stdout.log` / `stderr.log`：工具输出
- 工具自身的输出文件
- `incident.json`：触发原因与时间线

### 3. 评估影响

按顺序回答：

1. 目标业务是否出现异常？影响面多大？
2. 是否触及范围外资产或第三方系统？
3. 是否产生了数据读取、写入或配置变更？
4. 是否触发客户的安全告警？

影响不明时按最坏情况处理。

### 4. 通知授权方

15 分钟内联系 `scope.escalation.primary`，说明：

- 发生了什么（事实，不推测）
- 已采取的动作
- 当前影响判断
- 下一步计划

### 5. 无法解决则上报

满足任一条件即升级：

- 30 分钟内无法确认影响范围
- 业务异常持续存在
- 触及范围外资产
- 客户联系人无法联系

上报到 `scope.escalation.secondary`，并执行：

```bash
python scripts/incident.py --escalate .runs/<run_dir> \
  --reason "具体原因" --to "上报对象"
```

上报后在 `incident.md` 中记录时间、对象、结论。

## 禁止事项

- 不要为了"确认一下"继续扫描
- 不要删除日志或运行目录
- 不要在未通知客户的情况下尝试修复目标系统
- 不要把责任推给工具或网络，记录事实即可

## 事后

- 24 小时内补齐时间线与影响说明
- 复盘触发原因：参数、速率、工具版本、目标环境
- 把可复用的判断写进 `scope.json` 的排除项或新的前置检查
